# 초기 월드 생성: 현재 검증과 다음 단계

2026-11-14 Windows 디버그 빌드에서 구조물이 켜진 시드 `1`과 `-1`의
초기 생성·플레이어 스폰·임시 저장 파이프라인을 각각 실행했다. 저장된
지형의 섹션, 높이맵, 블록 엔티티, 예약 틱과 후처리 표시를 생성 초안과
비교했다. 이 파이프라인은 실제 저장 폴더에 월드를 게시하거나 게임을
시작하지 않는다.

같은 날 시드 `-1` 임시 월드의 지형 청크 11개와 엔티티 청크 1개를 Java
26.3 직렬화기로 읽고 다시 썼으며 엔티티 헤더 2개를 확인했다. POI 청크는
없었다. 이 검사는 Java 게임에서 월드를 열거나 Java가 같은 시드로 생성한
지형과 블록별로 비교하지 않는다. 검사한 등록 청크에서는 준비된 폐허 포털
시작점이 없어 폐허 포털 저장·배치를 확인하지 못했다.

이전 기록의 시드 `-1` 초기 생성 실패는 현재 확인한 설정에서는
재현되지 않았다. 이는 해당 시드의 모든 구조물이나 월드 생성이 바닐라와
같다는 뜻은 아니다.

이전에는 생성한 시드 `-1` 임시 월드에서 주변 9개 청크를 불러오고 한 틱을
진행했을 때, 저장 준비가 조명 처리 뒤 울타리 이웃 갱신에서 멈췄다. 대기 중인
`(30, 26)` 청크는 저장되어 있었지만 `(28, 24)`는 완성된 저장 청크가 아니었다.
누락된 청크를 생성·후처리하고 같은 세션에 반영하기 전에는 해당 저장 초안을
승인하지 않는다. 틱을 추가로 진행하지 않고 이미 대기 중인 조명만 처리하는
저장 준비 경계는 합성 월드에서 확인했다. 조명 처리로 바뀐 청크를 캡처 대상에
추가하며, 필요한 조명 입력이 없으면 계속 보류한다. 이 경계는 실제 게임의
저장 버튼이나 미생성 청크 생성에 아직 연결되지 않았다.

구조물이 켜진 초기 생성 결과는 게시 전 요청한 청크를 추가 생성할 수 있다.
기존 후처리 기록과 생성 엔티티를 확인하고, 블록·바이옴은 내부 번호가 아닌
실제 상태로 비교한다. 시드 `-1`에서 `(28, 24)`를 요청해 20개 청크를 임시
저장했고, 추가 청크의 바이옴 1,536개를 Java 26.3과 비교했다. 이는 특정
시드와 청크의 검사이며 생성 화면이나 플레이 중 생성에 연결되지는 않았다.

같은 임시 월드의 복사본을 플레이 세션으로 열어 필요한 이웃 형태 갱신을 처리한 뒤,
블록·유체·예약 작업을 바꾸지 않는 거품 기둥 예약 틱을 소비해 저장할 수 있다.
공기와 종유석·유황 첨탑 예약 틱도 보존하며, 혼합된 틱의 순서와 지연 시간 등을
Java 26.3 직렬화기로 비교했다. 해당 복사본을 다섯 차례 저장·재열기하여 기록된
블록 변경 245개와 플레이어 상태·시간을 확인했다. 틱을 실제 20 TPS 속도에 맞춘
추가 실행에서는 블록 변경 249개를 확인했다. 같은 시드로 월드를 처음부터 생성한
별도 검사에서도 플레이 뒤 저장된 블록 변경 243개와 플레이어 상태·시간을 확인했다.
거품 기둥 저장 처리를 확장한 뒤 같은 생성 검사에서 변경 249개를 다시 확인했다.
검증된 이웃에서 거품 기둥 예약 틱이 블록을 바꾸면 해당 블록과 새 블록·유체 틱을
함께 저장 초안에 포함한다. 블록과 예약 순서는 Java 26.3의 4,320개 콜백 조건과
비교했고, 혼합된 두 예약 틱 목록을 Java 코덱으로 읽어 예약 목록에 복원한 뒤 다시
꺼냈다. 주변 블록 변경에 따른 거품 기둥 형태 갱신도 관련 예약 틱을 보존한다.
이웃 갱신 72조건을 Java와 비교했고, 두 청크 경계에서 생긴 블록·유체 틱을 각각의
청크 초안에 보존하는 사례를 검사했다. 지원하지 않는 이웃과 결과를 확인할 수 없는
효과는 계속 저장을 차단한다. 거품 기둥 위치에 남은 다른 유체의 오래된 예약 틱은
Java 서버처럼 실행하지 않고 소비하며, 실제 서버의 여섯 조건과 저장 초안을 확인했다.
거품 기둥의 원천수 유체 틱이 검증된 빈 공간으로 퍼지는 경우에는 블록 변경과
블록·유체 예약 틱도 저장 초안에 포함한다. 물 수원 생성 규칙, 이웃 블록과 축,
데이터팩 유체 태그를 달리한 91,952개 조건에서 상태·예약 순서·난수 상태를 Java
26.3과 비교했다. 저장한 블록 팔레트와 유체 틱은 Java 코덱으로 읽고 다시 썼으며,
합성 월드를 저장·복원해 후속 틱과 두 청크 경계의 변경도 확인했다. 활성 물·용암
태그가 없거나 지원 범위를 벗어나고, 필요한 청크 또는 이웃 상태를 확인할 수 없으면
저장은 계속 차단한다. 다른 유체 상호작용과 엔티티 접촉 등은 별도 검증이 필요해
일반적인 플레이 후 저장은 아직 보장하지 않는다. 이 검사는 Java로 월드 전체를
생성하거나 양쪽 구현에서 번갈아 저장한 검사가 아니며, 실제 게임의 저장 기능에도
연결되지 않았다.

시드 `-1`의 폐허 포털 후보 `(20, 19)`를 초기 월드에 추가하는 검사에서는,
주변 구조물 조사 중 `(9, 21)`의 대저택 후보가 미지원 오류를 냈다. Java 26.3은
이 위치의 바이옴 열에서 가능한 대저택 바이옴이 없어 생성을 거부한다. 대저택의
바이옴 열 검사 위치와 세 시드의 72조건을 Java와 비교했고, 기본 선택과 합성 전체
바이옴 선택에서 불가능한 후보 34개는 건너뛰고 가능한 후보 38개는 계속 미지원으로
처리했다. 대저택 배치 자체와 폐허 포털이 포함된 완성 월드는 별도 검증이 필요하다.
후속 생성은 포털 중심 청크 `(21, 19)`의 템플릿 경계에서 자갈 이웃 갱신을 만났다.
포털 경계의 모래·붉은 모래·자갈은 Java처럼 낙하 블록 틱을 예약한다. 블록 세 종류,
여섯 방향과 네 이웃 상태의 72조건을 Java 26.3과 비교하고, 중복 예약과 프로토청크
저장 틱을 확인했다. 이 비교는 포털 전체 배치나 월드 왕복을 증명하지 않는다.
같은 포털의 물·용암 경계 갱신은 유체 수위와 방향, 이웃 블록 및 거품 기둥 관련
유체·블록 태그를 바꾼 18,816조건에서 Java 26.3과 비교했다. 유체·블록 예약 틱의
종류와 중복 제거, 프로토청크 저장 값을 확인했다. 전체 유체 상호작용이나 포털 배치
결과를 비교한 검사는 아니다.
포털의 담장과 철창이 물·용암을 이웃으로 만날 때는 활성 담장 및 기둥 덮어쓰기 태그를
적용한 뒤 연결과 기둥 모양을 갱신한다. 블록 상태, 여섯 방향, 유체 수위와 위쪽 블록,
태그 변경을 포함한 46,080조건의 상태와 예약 틱을 Java 26.3과 비교했다.
포털 경계에서 구리 광석 등 일반 광석과 원석 블록도 형상 변경 없이 처리하고,
담장·철창이 이 블록의 단단한 면에 연결되도록 했다. 레드스톤 광석의 발광 상태를
포함한 396조건의 갱신과 이웃 연결을 Java 26.3과 비교했다. 포털 장식에서 검증된
광석을 네더랙이나 마그마로 교체할 때 44가지 합성 사례의 블록, 높이맵, 예약 틱과
마그마 후처리를 확인했다. 교체 전 광석에 블록 엔티티, POI나 후처리 표시가 없다는
사실도 Java 26.3에서 확인했다. 전체 포털 배치나 교체에 따른 조명은 아직 별도로
검증해야 한다.
다음 장식 단계에서 다시마가 포털의 우는 흑요석을 지지 블록으로 만나는 사례를
처리하도록, 포털에 쓰이는 속성 없는 고체 17종의 렌더링 고체 여부와 여섯 면의
지지 판정을 Java 26.3과 비교했다. 잘못된 속성이 붙은 일부 상태는 계속 거부한다.
이 검사는 포털 전체와 다시마 배치 결과의 바닐라 일치를 보장하지 않는다.
포털의 계단과 반 블록 다섯 종류는 방향·모양·물에 잠긴 상태를 포함한 178개
상태에서 고체 렌더링과 여섯 방향의 지지 판정을 Java 26.3과 비교했다.
포털 고체 블록 17종의 빛 감쇠·발광과 조명 형상 사용 여부를 Java와 비교하고,
우는 흑요석과 이끼 낀 돌 벽돌이 포함된 3×3청크 합성 지형의 가운데 청크에서
초기 블록 조명 16,384개 값을 Java 조명 엔진과 비교했다. 이는 생성 중 포털
배치에 따른 모든 조명 갱신이나 완성 월드의 조명을 검증한 것은 아니다.
시드 `-1`에서 포털 시작 청크 `(20, 19)`와 중심 청크 `(21, 19)`는
난이도·엔티티 생성 문맥을 갖춘 별도 생성 작업에서 조명 단계까지 도달했다.
스폰을 찾은 초기 월드에 이 청크를 확장하는 검사에서는 이웃 `(21, 21)`의
해저 유적 템플릿이 해초를 교체할 때 중단됐다. 해초가 있거나 없는 합성
유적 배치 두 사례에서 완성 블록과 물 잠김, 블록·유체 예약 틱을 Java의 실제
템플릿 배치와 비교했다. 같은 시드에서 이웃 청크 `(21, 21)`을 포함한 별도
생성 검사는 교체 뒤 주변 해초의 이웃 형상 갱신에서 중단됐다. 해초의 지지
블록, 여섯 방향, 이웃 블록과 데이터팩 태그를 달리한 648조건에서 상태와 물 틱
중복 제거를 Java 26.3과 비교했으며, 구조물과 나무의 경계 갱신에 필요한 활성
태그를 준비한다. 후속 청크 생성에서는 앞서 생성된 수상한 자갈을 다른 유적
조각이 교체하는 사례가 나타났다. 생성된 수상한 모래·자갈 엔티티의 제거와 다른
엔티티·예약 틱 보존을 Java 26.3의 실제 `WorldGenRegion` 및 프로토청크와 8조건에서
비교했다. 같은 자리의 수상한 블록을 다시 배치할 때 장벽 쓰기와 새 블록 엔티티,
전리품 시드 및 기존 예약 틱을 Java와 비교했다. 다른 대기 엔티티 12개가 있을 때
임시 `DUMMY` 기록의 삽입·삭제와 남은 대기 엔티티의 저장 순서도 확인했다.
기록이 없는 블록 엔티티는 계속 거부한다. 다음 생성 검사에서는 유적 주변 단일 상자의
형상 갱신에서 중단됐다. 방향·물 잠김·이웃 방향과 종류를 달리한 208조건에서
단일 상자의 상태와 물 틱 중복 제거를 Java와 비교했다. 이중 상자와 수평으로 인접한
동일 상자의 갱신은 아직 거부한다. 같은 청크의 별도 생성 재검사는 이후 다시마 줄기
(`minecraft:kelp_plant`)의 이웃 형상 갱신에서 중단됐다. 다시마 줄기·끝부분의
지지 블록, 방향, 데이터팩 태그와 두 난수 방식에 따른 상태·예약 틱·난수 상태를
Java 26.3의 실제 형상 갱신 2,848조건과 비교했다. 해저 유적에서는 줄기를 끝부분으로
바꿀 때 드라운드 생성과 같은 지역 난수를 사용하며, 성공과 실패 시 복구도 검사했다.
지역 난수가 전달되지 않은 다른 생성 경로에서는 난수가 필요한 변환을 계속 거부한다.
다시마 갱신 뒤의 생성 검사에서는 수상한 자갈 위 해초의 지지면 판정에서 중단됐다.
수상한 모래·자갈의 네 먼지 단계와 여섯 면 48조건을 Java와 비교했고, 해초의 형상
갱신 1,224조건과 실제 장식 배치 10,752조건에서 활성 태그와 반복 배치도 비교했다.
다음 검사에서는 같은 청크의 조명 단계에서 수상한 자갈의 미지원 조명 속성 때문에
중단됐다. 수상한 모래·자갈 8개 상태의 빛 차단·발광·조명 형상을 Java와 비교했고,
이 블록을 포함한 합성 청크의 블록빛·하늘빛 배열을 Java 조명 엔진과 대조했다.
이는 전체 월드 조명이 동일하다는 뜻은 아니다.
초기 월드 확장의 재검사와 임시 월드의 포털 시작점·참조에 대한 Java 비교는 아직
실행되지 않았다.

구조물 생성이 켜진 기존 월드에서도 혼합 캡처 지형의 장식 단계에 빈 구조물
참조와 저장된 묻힌 보물 참조를 사용할 수 있다. 보물의 변경된 시작점은 원본에
연결된 별도 초안으로 보존한다. 원본 청크가 후처리 대상 밖이면 그 원본을
별도 초안으로 반환하며, 향후 저장은 생성 청크와 원본 변경을 함께 처리해야
한다. 합성 저장 청크에서 기존 저장 청크 장식 경로와
블록 및 구조물 NBT를 비교하고, 미지원 참조와 실패 시 상태 보존을 검사했다.
다른 구조물, 새 구조물 시작점, 플레이 중 생성과 월드 저장은 아직 이 경로에
연결되지 않았다.

저장 계획은 완성된 새 청크 리전과 저장된 보물 시작점의 높이 변경을 한 번에
추가하고 같은 트랜잭션으로 기록할 수 있다. 원본의 다른 NBT는 보존하며,
데이터팩·설정·원본과 새 청크 및 엔티티·POI 부재를 캡처하고 재확인해야 한다.
임시 월드에서 프로토청크 보존, 원본 변경 시 중단과 서로 다른 리전의 원자적
저장을 검사했다.
캡처된 후처리 결과는 기존 POI 저장 데이터가 없는 청크에 대해 블록 상태로
POI 초안을 구성한다. 기존 POI가 있는 청크는 미확인 상태로 남기며, 저장
전에 디스크와 라이브 티켓 상태를 다시 확인해야 한다. 엔티티 및 나머지 저장
완전성도 아직 확인되지 않아 이 결과로 실제 월드 저장을 승인하지 않는다.
구조물과 몹 생성이 없고 이웃 장식·저장 엔티티·후처리 드롭도 없는 경우에만
해당 청크의 캡처·생성 엔티티가 없다는 증거를 보관한다. 다른 저장 청크와
라이브 엔티티가 아직 완전히 검증되지 않아 전체 엔티티 기록은 미확인으로 남긴다.
후처리는 각 블록의 변경 전후 상태를 순서대로 기록한다. 같은 위치가 다시
바뀌어 최종 블록이 원상태가 된 경우에도 POI 변경을 놓치지 않는다. POI가
실제로 바뀐 후처리 결과는 Java의 갱신 순서와 기존 티켓을 반영하는 경로가
검증될 때까지 블록만으로 POI 초안을 만들지 않는다.
Java 26.3의 `WorldGenRegion.setBlock`도 POI 변경을 서버에 예약한다. 따라서
장식 단계에서 해당 쓰기의 POI 변경을 청크별로 기록하며, 광맥의 직접 섹션
쓰기는 이 기록에 포함하지 않는다. 서버 큐의 실행 순서와 기존 POI를 아직
재현하지 않았으므로 생성 중 POI 변경이 있는 청크의 스냅샷 구성도 중단한다.
실행 순서가 별도로 확인된 POI 알림은 기존 저장 기록에 순서대로 적용할 수
있다. 같은 종류의 기존 POI와 티켓을 유지하고, 다른 종류로 덮어쓸 때 Java의
해시 슬롯 순서를 보존한다. 이 초안은 서버 큐의 순서, 라이브 POI 인덱스나
티켓 변경을 증명하지 않으며 실제 월드 저장을 승인하지 않는다.

다음 순서로 진행한다.

1. 폐허 포털 시작점과 참조가 실제로 포함되는 시드·청크를 고정하고,
   배치 결과와 저장된 시작점·참조를 Java 26.3과 비교한다. 그 밖의 미지원
   구조물과 엔티티도 생성 중 명시적으로 실패하는 사례부터 처리한다.
2. 여러 시드·설정·데이터팩에 대해 생성 결과와 Java의 지형·구조물·엔티티를
   비교하고, 임시 저장본을 양쪽 구현에서 열고 저장하는 왕복을 검증한다.
3. 검증한 생성과 저장을 생성 화면의 진행 상태·취소·오류 처리에 연결한다.
   완전성과 안전성이 확인된 결과만 실제 저장 폴더에 게시하고 세션을 연다.
4. 플레이 중 빠진 청크 생성·저장과 재접속 복원을 연결하고, 경계 이동과
   취소·실패 시 기존 데이터 보존을 검사한다. 이후 세 차원과 사용자
   데이터팩으로 범위를 확장한다.
5. 릴리스 빌드에서 각 생성 단계의 시간과 메모리를 측정하고, 결과 및 틱·난수
   순서를 유지하는 최적화만 적용한다. 화면 성능은 별도 조건에서 측정한다.
