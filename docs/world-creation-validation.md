# 새 월드 생성과 플레이 연결 검증 계획

## 현재 확인한 범위

작업 트리의 `generated_world_spawn_chunk_round_trips_through_java` 검사는
구조물이 켜진 시드 `-1` 오버월드를 임시로 생성한다. 생성한 플레이어의
저장된 지형 청크를 리전 파일에서 열거하고 Java 26.3의
`SerializableChunkData`로 읽고 다시 쓴 뒤 블록, 바이옴, 조명과 일부 청크
데이터를 비교한다. 저장된 엔티티 청크의 좌표, 엔티티 식별자와 위치를 Java에서
읽고 NBT를 다시 쓴 뒤 필드 값을 비교한다. `level.dat`, 월드 생성 설정과
플레이어의 위치·차원·UUID도 검사한다.

2026-11-08 Windows 디버그 빌드에서 지형 청크 11개와 엔티티 청크 1개
(엔티티 헤더 2개)의 검사가 통과했으며 실행 시간은 약 363초였다. 이 월드에는
저장된 POI 청크가 없어 실제 POI 검사는 실행되지 않았다. 이 결과는 한 월드의
검사한 필드에 한정된다. 엔티티 전체를 Java 객체로 읽은 것이 아니고 Java 게임
자체에서 월드를 열거나 플레이한 결과도 아니다. POI, 사용자 데이터팩 및 나머지
차원의 보존을 증명하지 않는다. 이 검사의
작업자 변경과 Java 검사 코드는 현재 별도 미커밋 작업에 포함되어 있다.

2026-11-10 같은 Windows 환경에서 현재 작업 트리로 다시 실행한 결과도
지형 청크 11개와 엔티티 청크 1개(엔티티 헤더 2개)를 통과했다. POI 청크는
없었으며, 초기 플레이 세션의 대상 청크에는 비어 있지 않은 엔티티 청크가
없었다. 검사는 약 145초가 걸렸다. 시간은 단일 디버그 실행으로, 릴리스
성능이나 이전 실행과의 성능 차이를 판단하는 기준이 아니다. 이번 검사도 Java
게임 실행 및 전체 엔티티 동작의 왕복을 포함하지 않는다.

같은 시드의 생성 리전 초안을 신규 청크 저장 트랜잭션으로 빈 임시 월드에
기록한 뒤 동일한 Java 검사를 다시 수행했다. 2026-11-08 Windows 디버그
빌드에서 지형 청크 11개, 엔티티 청크 1개(엔티티 헤더 2개)가 통과했고
POI 청크는 없었다. 저장된 청크 좌표 집합이 기존 스테이징 결과와 같은지도
확인했다. 이 경로는 작업 트리의 미커밋 생성 검사에 추가되어 있으며 실행은
약 530초였다. 한 시드와 검사한 필드에 한정되고, 실제 Java 게임에서 월드를
열거나 기존 월드의 주변 청크와 함께 생성한 검사는 아니다.

별도의 합성 검사에서는 Java 26.3이 기존 리전과 새 리전에 추가한 지형 두
청크 및 엔티티·POI 항목을 읽고 기존 청크가 유지되는 것을 확인했다. 이 검사는
저장 형식의 일부를 확인하며 실제 월드 생성 결과의 바닐라 일치를 뜻하지 않는다.

수중 마그마가 나무 판자나 원목 계열을 이웃으로 만날 때의 면 판정을
Java 26.3과 비교했다. 바닐라 나무 상태와 여섯 방향의 978개 조합이
일치하며, 미지원 이웃을 만났을 때는 생성 중인 변경을 되돌린다. 이 검사는
마그마 인접 블록의 면 판정에 한정되고 전체 구조물·월드 생성을 보증하지 않는다.
반 블록과 계단도 방향별 면을 판정한다. 설치된 26.3의 8,366개 상태와
50,196개 면을 Java와 비교했으며, 아래·위·이중 반 블록에 따른 실제 마그마
배치 여부를 별도로 검사한다.

## 게시 전 검증 순서

1. 임시 월드에 저장된 모든 지형·엔티티·POI 청크와 해당 좌표를 열거한다.
   Java가 각 청크를 읽고 다시 쓴 뒤 블록, 바이옴, 조명, 높이맵, 구조물,
   블록 엔티티, 예약 틱, 후처리 표시와 엔티티·POI 데이터를 비교한다.
   누락된 청크와 빈 청크의 의미도 각각 확인한다.
2. 여러 시드와 구조물 설정, 보너스 상자, 게임 모드와 데이터팩을 검사한다.
   네더·엔드와 사용자 차원도 생성 및 저장 경로가 준비되는 대로 같은
   검증에 포함한다. 설치된 Java의 원본 월드와 비교할 때는 복사본만 쓴다.
3. Java에서 임시 월드를 열어 저장한 뒤 다시 읽고, 구현체에서도 열고
   저장한 다음 Java로 재확인한다. 플레이어·게임 규칙·시간·날씨·데이터팩과
   미지원 데이터가 유지되는지 검사한다.
4. 위 검증과 생성 데이터 완전성 검사를 통과한 경로만 실제 저장 폴더에
   게시한다. 오류 또는 취소 시 기존 월드를 변경하지 않고 재시도할 수
   있어야 한다. 생성 화면의 진행 상태와 취소를 작업자에 연결하고, 생성
   직후 세션을 시작한다.
5. 플레이 중 미생성 청크의 생성과 저장, 재접속 후 플레이어 복원을 연결하고
   각 단계의 실패·취소·경계 이동을 검사한다. 검증하지 않은 기능은 완성이나
   바닐라 호환으로 표시하지 않는다.

플레이 중 생성한 청크를 저장하기 위한 기반으로, 새 지형과 엔티티·POI의
저장 여부를 하나의 저장 계획에 추가할 수 있다. 세 항목 중 기존 데이터가
하나라도 있으면 전체 트랜잭션을 중단하며, 새 지형 리전의 생성도 중단 후
복구할 수 있다. 생성기의 완성된 리전 초안도 지형과 부속 데이터의 대응을
확인해 저장 계획으로 옮길 수 있다. 이 경로는 생성 결과의 완전성을 증명하지
않으며, 아직 게임 세션이나 이동 중 청크 생성에 연결되지 않았다.

생성이 참고한 기존 지형·엔티티·POI 청크와 비어 있던 청크는 저장 계획의
읽기 의존성으로 지정할 수 있다. 저장 전 원본이 바뀌었거나 비어 있던 리전이
생겼으면 트랜잭션을 중단하고, 읽기만 한 리전은 다시 쓰지 않는다. 호출자가
관찰한 모든 입력을 빠짐없이 지정해야 하며, 메모리의 미저장 변경과 생성 설정의
동시 변경은 별도로 보호해야 한다. 생성 작업자 연결은 아직 남아 있다.

잠긴 월드 리더에서 선택한 청크의 지형·엔티티·POI 원본을 함께 수집하고,
같은 월드 세션의 저장 계획에 의존성을 일괄 추가할 수 있다. 저장 전 리더가
보유한 리전 핸들을 닫으며 저장 중 새 리전 읽기는 오류를 반환하므로 호출자가
재시도해야 한다. 청크 스트리머는 지형과 부속 파일을 한 보호 구간에서 읽지만,
읽은 결과를 세션에 반영하는 시점과 저장은 여전히 별도로 조정해야 한다.
이 캡처에는 세션에서 아직 저장하지 않은 변경, 데이터팩 및 생성 설정이 포함되지
않으므로 실시간 청크 생성에 연결하기 전 별도 검증이 필요하다.

생성 설정 파일은 같은 월드 세션에서 별도로 캡처해 생성에 사용하고 저장 계획의
읽기 의존성으로 지정할 수 있다. 저장 전 원본 바이트가 바뀌면 중단하며,
저장 트랜잭션의 반영 전후에도 파일을 다시 확인한다. 다른 월드 세션의 캡처를
섞을 수 없다. 이 보호는 호출자가 설정 스냅샷을 실제 생성에 사용하고 저장 계획에
지정해야 적용된다. 데이터팩, 메모리의 미저장 변경과 생성 작업자 연결은 여전히
별도로 처리해야 한다.

생성 설정과 선택한 지형·엔티티·POI 원본은 하나의 쓰기 배제 구간에서 함께
캡처할 수 있다. 묶음을 저장 계획에 추가할 때 중복이나 다른 세션이 발견되면
계획에 일부만 추가하지 않는다. 캡처 뒤 설정 또는 이웃 청크가 바뀐 경우 저장이
중단되고, 다시 캡처한 입력으로 재시도하는 합성 검사를 추가했다. 캡처 도중
다른 스레드의 저장이 거부되는지도 확인했다. 이 캡처도
호출자가 필요한 모든 입력을 지정해야 하며 데이터팩과 미저장 게임 상태는 포함하지
않는다.

기존 월드의 캡처된 생성 설정으로 노이즈 생성기를 준비하는 경로를 추가했다.
활성 데이터팩이 같은 차원을 정의하면 저장된 차원보다 우선하며, 선택한 팩은
준비 과정에서 스냅샷으로 유지한다. 설치된 26.3의 세 차원에서 시드 -42의
원점 바이옴을 기존 프리셋 준비 경로와 비교했고, 합성 데이터팩의 차원 재정의와
구조물 비활성 설정을 검사했다. 이 경로는 아직 실행 중 청크 생성에 연결되지
않았고, 스냅샷이 해당 월드의 활성 팩과 일치하는지와 원본 팩의 변경을 보호하는
책임은 호출자에게 있다. 전체 지형의 Java 차등 검증은 별도로 필요하다.

## 성능 측정

디버그 실행 시간은 릴리스 성능의 기준으로 쓰지 않는다. 동일한 시드와
설정으로 릴리스 빌드의 준비·지형·구조물·장식·조명·저장 시간을 나누어
측정하고 CPU와 메모리 사용량을 함께 기록한다. 병목을 측정한 다음 결과와
틱·난수 순서를 보존하는 최적화를 적용하고, 변경 전후의 생성 결과를 다시
비교한다. 최종 화면 성능은 동일한 월드와 카메라의 1080p·12청크 조건에서
별도로 측정한다.
